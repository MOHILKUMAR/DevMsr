# Security

This describes how the platform protects visitor data and the admin area, what is tested, and what still needs attention. It is not a certification; see "Known limitations".

## Trust boundaries

| Actor | Can do | Cannot do |
| --- | --- | --- |
| Visitor (browser) | Read published catalogue pages; submit a lead form through the server | Read or write any table directly; see any lead; call server-only functions |
| Server, publishable key | Read active/published catalogue rows (RLS) | Read leads, admin profiles, notifications, audit log |
| Server, admin session | Whatever the signed-in admin's role allows (RLS + server checks) | Create or change admin profiles |
| Server, secret key | `create_lead`, `check_rate_limit`, `record_notification_event`, `purge_expired_leads`, notification activity rows | — (bypasses RLS; used only in `src/lib/leads` and the retry endpoint) |

The browser never receives a Supabase key: all database access happens in server code.

## Authentication and authorisation

- Admin sign-in uses Supabase Auth (email + password). Auth cookies are `HttpOnly`, `SameSite=Lax`, `Secure` in production.
- `src/middleware.ts` verifies the session on every `/admin` request, admin action and `/api/admin` call with `auth.getClaims()` (JWT signature check), then loads the **admin profile**. No active profile → redirect to sign-in (pages) or `401` (actions).
- Every admin mutation goes through `defineAdminAction` (`src/lib/admin/action.ts`): authenticate → check role capability → validate with Zod → write through the admin's own session so **RLS enforces the same rules in the database**.
- Roles come only from `admin_profiles`, which has no insert/update/delete policies: it can be changed only with SQL in the Supabase dashboard.
- Sign-in errors are generic; attempts are rate-limited per hashed IP (10/15 min) and per hashed email (10/hour) on top of Supabase's own limits.
- Post-login redirects accept only same-site `/admin` paths (`src/lib/auth/redirect.ts`).

## Row Level Security matrix

| Table | anon | authenticated (no profile) | editor | admin | owner |
| --- | --- | --- | --- | --- | --- |
| industries, services, service_industries, service_pricing, faqs, site_settings | read active | read active | read active | full | full |
| products, portfolio_projects, portfolio_industries, blog_posts | read published | read published | full | full | full |
| leads | — | none | none | read, update | read, update, **delete** |
| lead_activities | — | none | none | read; insert **notes as themselves** | same |
| notification_events | — | none | none | read, update | read, update |
| admin_profiles | — | own row | own row | own row | all rows (read) |
| audit_log | — | none | none | read | read |
| internal.rate_limits | not exposed through the API |

Verified by `tests/db/schema.test.ts`, which runs the real migrations on PGlite with Supabase-like roles (34 tests: permission denials, escalation attempts, inactive admins, note impersonation, owner-only deletes, audit entries, parameterised search).

## Lead intake defences (`src/lib/leads/submit.ts`)

1. **Zod validation on the server** — normalisation, length limits, enum allow-lists, control characters stripped. Client validation is a convenience only.
2. **Honeypot** — an off-screen field; filled → fake success, nothing stored.
3. **Signed form token** — HMAC of the render time; submissions faster than 3 s or older than 24 h are rejected.
4. **Turnstile** (when configured) — verified server-side with an idempotency key.
5. **Rate limits** — 5/hour and 20/day per hashed IP, 4/day per hashed email. Raw IPs are never stored.
6. **Idempotency** — the form's `submissionId` is unique in the database; resubmission returns the same reference. Identical email + description within 30 minutes is treated as a duplicate.
7. **Database constraints** repeat the important rules (email shape, lengths, enums, phone format, URL scheme).

## Output safety

- Astro escapes all template output. The only HTML injected with `set:html` is (a) JSON-LD, with `<` escaped, and (b) Markdown rendered by `src/lib/content/markdown.ts`, which escapes raw HTML and allows only `http(s)`, `mailto`, `tel`, anchors and site-relative links (images: `https` only).
- Email templates escape every visitor value.
- Admin-entered image and demo URLs must be `https://` (checked in Zod and in database constraints).

## HTTP security

- **CSP** (response header): `default-src 'self'`, hashed scripts and styles generated by Astro, Turnstile allowed, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`. No `unsafe-inline`. The pre-paint theme script's hash is computed at build time (`astro.config.mjs`).
- `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, HSTS on HTTPS.
- Admin pages, API routes, actions and form pages: `Cache-Control: private, no-store`; admin pages also `X-Robots-Tag: noindex`.
- CSRF: Astro's `security.checkOrigin` rejects cross-site form posts (tested); auth cookies are `SameSite=Lax`.

## Secrets

- Only `.env.example` (placeholders) is committed. `.dev.vars`, `.env*` are git-ignored.
- The Cloudflare tooling copies `.dev.vars` into `dist/server/` for local preview; `npm run check:secrets` deletes it and scans every browser asset for secret patterns and local secret values. `npm run deploy` runs this automatically.
- In production set secrets with `npx wrangler secret put <NAME>`.

## Logging

Structured JSON logs (`src/lib/server/logger.ts`) with a request id per request. Keys such as `email`, `phone`, `name`, `project_description`, `password`, `cookie`, `ip` are redacted automatically. Visitors never see stack traces or database errors.

## Data retention and deletion

- Retention: `public.purge_expired_leads()` deletes non-won leads with no activity for `lead_retention_months` (default 24), stated in the privacy policy. Schedule it with `pg_cron` (see SETUP).
- Erasure requests: an owner can permanently delete a lead from its detail page (type `DELETE` to confirm). Deletions are recorded in `audit_log` (without the deleted content).

## Backups

The Supabase Free plan has **no automatic backups**. Until you upgrade to Pro (7-day daily backups):

```bash
npx supabase db dump --linked -f backup-schema.sql
npx supabase db dump --linked --data-only -f backup-data-$(date +%F).sql
```

Store dumps encrypted, outside the repository. **Do not** add a GitHub Actions backup job to this repository while it is public: workflow artifacts would expose lead data.

Restore: create a project, apply `supabase/migrations`, then load the data dump with `psql`.

## Known limitations

- End-to-end flows against a live Supabase project (real sign-in, saving a lead, Resend delivery) are implemented and covered by local database and unit tests, but have not yet been run against your live services (pending credentials).
- No MFA for admin sign-in yet (Supabase supports TOTP; deferred).
- Rate-limit counters live in the database; a database outage disables lead intake (by design — leads cannot be saved anyway).
- The bundled-data fallback for public pages means an unreachable database shows the last *deployed* catalogue rather than the latest admin edits (logged as `catalogue.fallback`).

## Future AI features

When chatbots or agents are added (deferred), follow the brief's rules: treat visitor messages, documents and third-party responses as untrusted; keep system instructions separate; validate every model output with Zod before it touches the database; authorise each tool call independently; never expose keys or system prompts; require human approval for consequential actions; route all model calls through server endpoints with request and token budgets.
